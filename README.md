# Практика: Structured Outputs

Cоберем небольшой классификатор обращений в поддержку. Модель YandexGPT должна вернуть категорию, приоритет, краткое описание и признак ручной проверки. Все запросы идут через официальный OpenAI SDK: YandexGPT совместим с OpenAI API, поэтому меняются только `base_url`, `project` и имя модели. План совпадает со слайдом «Практика» в `presentation.md`.

Все команды выполняются из корня репозитория с активным виртуальным окружением.

## До занятия

Понадобятся:

- установленный `uv`
- Python 3.12.8, который `uv` может установить автоматически
- каталог Yandex Cloud с активированным API YandexGPT
- сервисный аккаунт с ролью `ai.languageModels.user`
- API-ключ сервисного аккаунта

Секрет нельзя добавлять в git, показывать на слайдах или печатать в терминал.

## 1. Подготовить окружение и контракт обращения в поддержку

Перейдите в папку демо и установите зависимости из `pyproject.toml`:

```bash
uv sync
```

Создайте локальный файл настроек:

```bash
cp .env.example .env
```

Заполните `.env`:

```dotenv
YC_API_KEY=<API-ключ сервисного аккаунта>
YC_FOLDER_ID=<идентификатор каталога>
YC_MODEL_URI=gpt://${YC_FOLDER_ID}/yandexgpt/latest
YC_BASE_URL=https://ai.api.cloud.yandex.net/v1
```

Откройте `src/lib/llm_client.py` и посмотрите функцию `build_client`. Это весь код подключения:

```python
OpenAI(
    api_key=settings.api_key,
    base_url=settings.base_url,
    project=settings.folder_id,
)
```

Без `base_url` и `project` тот же SDK отправит запрос в OpenAI, а не в Yandex Cloud.

Откройте `src/lib/models.py`. Класс `TicketClassification` является единым контрактом для Python-кода и модели. Обратите внимание на:

- перечисления `TicketCategory` и `TicketPriority`
- обязательные поля
- ограничения длины `summary`
- `extra="forbid"` для запрета неизвестных полей

Посмотрите схему, которую Pydantic построит из класса:

```bash
python3 tests/test_show_schema.py
```

Ожидаемо: в терминале появится JSON Schema с объектом `TicketClassification`, обязательными полями и `additionalProperties: false`. 


`additionalProperties: false` - запрет добавления новых полей в JSON Schema.

## 2. Увидеть проблемы свободного текста

Запустите обычный запрос без структурированного вывода:

```bash
python3 src/main/01_unstructured.py
```

Ожидаемо: модель классифицирует обращение, но форма ответа зависит от генерации. Это может быть текст, Markdown или JSON в кодовом блоке. Прикладному коду пришлось бы извлекать данные эвристиками.

Проверьте `01_unstructured.py`:

- контракт передан модели только словами
- параметр `response_format` не передается, формат ответа ничем не ограничен
- результат нельзя безопасно передать следующему сервису без разбора и проверки

Если запрос завершился ошибкой `401` или `403`, проверьте API-ключ, роль сервисного аккаунта и значение `project`. При сетевой ошибке проверьте доступ к `https://ai.api.cloud.yandex.net`.

## 3. Сравнить JSON Object с проверкой Pydantic

Запустите запрос с `response_format={"type": "json_object"}`:

```bash
python3 src/main/02_json_object.py
```

Ожидаемо: API вернет синтаксически корректный JSON. Затем скрипт попробует создать `TicketClassification`.

Возможны два результата:

- `Контракт пройден` - модель выбрала все поля и допустимые значения
- `JSON валиден, контракт нарушен` - JSON разбирается, но тип, поле или значение не соответствует модели Pydantic

Главный вывод: JSON Object решает синтаксическую задачу, но не гарантирует прикладную схему.

В `02_json_object.py` найдите две независимые границы:

1. `json.loads()` проверяет синтаксис JSON.
2. `TicketClassification.model_validate()` проверяет структуру и типы.

## 4. Получить ответ по JSON Schema

Запустите schema-constrained запрос:

```bash
python3 src/main/03_json_schema.py
```

Скрипт:

1. получает JSON Schema через `TicketClassification.model_json_schema()`
2. передает ее в `response_format={"type": "json_schema", "json_schema": {...}}`
3. получает JSON, ограниченный схемой на этапе генерации
4. повторно валидирует ответ через Pydantic

Ожидаемый ответ имеет такой вид:

```json
{
  "category": "billing",
  "priority": "high",
  "summary": "После двойного списания клиент просит вернуть лишний платеж",
  "requires_human": true
}
```

Формулировка `summary` может отличаться, но набор полей, типы и значения перечислений должны соответствовать контракту.

Сравните три режима, которые в коде отличаются только значением `response_format`:

- без `response_format` нет гарантии даже валидного JSON
- `{"type": "json_object"}` гарантирует JSON, но не схему
- `{"type": "json_schema", ...}` ограничивает структуру ответа заданным контрактом

Посмотрите `build_response_format` в `llm_client.py`: все три режима собираются в одной функции, а сам вызов `client.chat.completions.create` остается одинаковым.

## 5. Проверить ошибки контракта без обращения к LLM

Запустите локальные примеры:

```bash
python3 tests/test_validate_examples.py
```

Ожидаемо:

```text
valid: контракт пройден
wrong_enum: контракт отклонен
missing_field: контракт отклонен
extra_field: контракт отклонен
Итого: 1 принято, 3 отклонено
```

Откройте `tests/test_validate_examples.py` и по очереди исправьте один невалидный пример. Повторите запуск и убедитесь, что счетчики изменились.

Обратите внимание, что Structured Outputs не проверяет:

- истинность фактов в `summary`
- соответствие категории внутренним правилам компании
- допустимость автоматического действия для конкретного клиента
- актуальность схемы у сервиса-получателя

## Итог практики

Получился минимальный надежный контур:

```text
текст обращения -> JSON Schema в response_format -> структурированный JSON -> Pydantic -> прикладной сервис
```

Схема ограничивает форму генерации, а локальная валидация защищает границу приложения. Оба механизма нужны одновременно.
